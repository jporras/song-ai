# Gemma: HTTP 400 al pedir cambiar la voz — 2026-10-15

Al abrir Song AI con el lanzador y preguntar por la voz de Alma, la interfaz mostró guía local con `HTTP Error 400`. El servidor Gemma estaba sano (`/health: ok`); su log registró tres rechazos de `/completion`: **11 906 tokens de entrada frente a 8192 de contexto**. El proyecto profesional completo se insertaba en el estado conversacional, incluida `_provenance` extensa y datos históricos. La ficha vigente de Alma tiene `user_confirmation_status=pending`; los archivos finales visibles son artefactos históricos y su descarga bloqueada es el gate correcto de la revisión actual.

`conversation_state` conserva ahora revisión, campos actuales y origen/confirmación por campo; excluye cuerpos de procedencia, snapshots privados, artefactos y eventos ya redundantes. El contrato persistido de SQLite no cambia. El cliente llama.cpp muestra el detalle estructurado del HTTP 400 si reaparece, en lugar de solo `Bad Request`.

Comprobación sin escribir la ficha: mensaje recompuesto con set y proyecto Alma de la API, steering vigente y la misma petición de voz. `/tokenize` contó **5771 tokens**; `/completion` respondió HTTP 200 con texto pertinente en 69,31 s. Esa prueba limitó la salida a 128 tokens y terminó por límite, así que acredita que desapareció el rechazo de contexto, no una respuesta completa de la app ni aceptación de un cambio de voz. Diecinueve pruebas dirigidas Python pasaron. Para usar el código corregido en la sesión abierta, reiniciar Song AI desde el lanzador; los servidores LLM y proyectos del usuario no se reiniciaron durante esta verificación.
